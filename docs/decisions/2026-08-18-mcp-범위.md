# 2026-08-18 MCP 1단계 범위 결정

## 논의한 것

A. 명세(`bordo-openapi.yaml 0.0.4`)의 `deputy_` 13종을 한 번에 구현
B. **쓰기 도구 3종만** 먼저 붙이고, 읽기·동기화·대리인 질문은 2단계로

그리고 그 밑에 딸린 것 — 도구 이름 접두사(`deputy_` → `bordo_`), 토큰 접두사(`dpt_` → `brd_`),
프로토콜 세대(legacy `initialize` / modern `server/discover`), 세션·SSE 유무, `states` 구역의
`source` 필드.

## 결정

**B.** 1단계는 `bordo_record_work` · `bordo_upload_document` · `bordo_complete_work` 3종.

| 항목 | 결정 |
|---|---|
| 도구 접두사 | `bordo_` — 도구 이름은 사용자 AI 대화창에 그대로 찍힙니다. 조직·저장소가 이미 Bordo 인데 `deputy_` 가 뜨면 무슨 서비스인지 모릅니다. 구현체가 없는 지금이 비용 0 으로 바꿀 마지막 시점 |
| 토큰 접두사 | `brd_` — 위와 같음 |
| 프로토콜 | **dual-era.** legacy(≤ `2025-11-25`, `initialize` 핸드셰이크)와 modern(`2026-07-28`, `server/discover` + `_meta` 판 번호) 둘 다 받습니다. 한쪽만 만들면 클라이언트 종류에 따라 연결 자체가 안 됩니다 |
| 세션(`Mcp-Session-Id`) | 안 만듭니다. 최신 판에서 삭제됐고, Bearer 토큰이라 요청마다 사용자를 압니다 |
| SSE 스트림 | 안 만듭니다. 도구가 전부 짧은 쓰기입니다 |
| 도구 실행 오류 | JSON-RPC `error` 가 아니라 **`result.isError: true`** — `error` 로 내면 클라이언트가 프로토콜 문제로 취급해 모델에게 안 보여주고, AI 는 같은 호출을 반복합니다 |
| `project_id` 생략 | 가장 최근에 연 프로젝트. 결과에 `resolved_by: "default"` 를 반드시 돌려줍니다 |
| `StateBase.source` (`web` · `mcp` · `agent`) | 추가. 화면 뱃지 「개인 AI가 기록함」은 항목 자체에 출처가 있어야 그립니다 |
| `states` 검증 로직 | `apps/states/services.py` 로 분리해 뷰와 MCP 가 같은 함수를 지납니다 |
| 나머지 10종 | 명세 `/mcp` 의 `x-deferred-tools` 에 이름만 남깁니다. 지우면 2단계에서 다시 설계해야 합니다 |

## 근거

- **읽기 도구가 없는 것이 보안 설계입니다.** MCP 토큰은 개발자 컴퓨터의 설정 파일에 평문으로 앉는
  장기 자격증명이라 실수로 커밋될 수 있습니다. 쓰기만 있으면 새더라도 가져갈 게 없고, 그 사람
  이름으로 기록을 쓰는 것뿐이며 `ActivityEvent` 에 남아 보입니다. 읽기를 붙이는 2단계에는 토큰
  만료가 같이 와야 합니다.
- 명세가 `protocolVersion: '2024-11-05'` 로 적혀 있었는데 그 판은 deprecated 이고, 그 사이 MCP 명세가
  네 번 바뀌었습니다. 명세대로 만들면 modern 클라이언트가 붙지 않습니다.
- 명세의 `tools/call` 결과가 `content[]` 없이 맨 객체였습니다 — 그대로 내보내면 클라이언트가 결과를
  파싱하지 못합니다. `structuredContent` + `content[0].text` 로 고쳤습니다.
- 현재 상태(work)는 본인 것을 본인 컴퓨터의 AI 가 본인 토큰으로 씁니다. 승인 단계를 넣으면 "내가
  방금 말한 걸 내가 다시 승인"하는 꼴이라 아무도 안 누릅니다. 반면 태스크·일정은 남에게 할 일을
  만드는 것이라 `PENDING_APPROVAL` 이 그대로 유지되고, 그래서 1단계 도구 셋에 `propose_task` 가
  없습니다.

## 반대 의견

- (이전 결정) 13종을 한 번에 — 명세가 이미 있으니 다 만들자는 쪽. 작업량이 2배 이상이고
  동기화(`SyncConflict` · 3-way diff)와 정책 제안 모델이 아직 없어 이번에 넣지 않았습니다.
- `states` 구역은 D 담당이라 `source` 필드와 검증 분리를 D 가 직접 올리는 것이 역할 기록에
  맞다는 의견 — 일정상 이번 PR 에 함께 넣되 여기 기록으로 남깁니다.
